# Dual-Market ML Meta-Label Design

**Date:** 2026-07-17
**Status:** Approved design; implementation pending

## Summary

Market Sentinel will replace its synthetic demonstration model with two independently trained and validated daily-bar machine-learning lanes:

- `SPY` using Alpaca historical data and Alpaca paper trading.
- `NIFTYBEES` using Groww historical data and Market Sentinel's local paper simulator.

Each lane uses a regularized logistic-regression meta-labeler to filter a deterministic long-only trend strategy. The model can reject or rank candidate entries, but it cannot create an order, size a position, change runtime mode, bypass risk or compliance, activate live trading, or call a broker.

The build ends at historical validation and paper operation. It does not promise a loss-free system, 90 percent accuracy, profit, or future performance, and it does not submit a real-money order during implementation or verification.

## Problem

The current `train-model` command trains a hand-written linear classifier on synthetic momentum and volume examples. Model promotion is based on a fixed 90 percent classification-accuracy threshold. This is not evidence of market performance because:

- the training rows are generated by the application rather than obtained from a market-data source;
- the model can evaluate on its training rows when a validation set is omitted;
- ordinary accuracy ignores fees, spread, slippage, expectancy, drawdown, coverage, and probability calibration;
- there is no chronological walk-forward evaluation or purge gap;
- SPY and NIFTYBEES do not have independent datasets, models, thresholds, and validation records; and
- the current model artifact does not preserve enough data and trial lineage to audit selection bias.

## Goals

- Train on real daily OHLCV bars obtained from the configured broker data APIs.
- Keep SPY and NIFTYBEES data, models, costs, thresholds, and validation results isolated.
- Generate every feature using information available by the decision timestamp.
- Use ML only as an advisory filter over deterministic candidate signals.
- Evaluate candidates after market-specific costs and protected-trade rules.
- Validate with expanding chronological walk-forward folds and a purge gap.
- Replace the accuracy-only gate with explicit out-of-sample promotion criteria.
- Version models, datasets, feature definitions, cost assumptions, and trial metadata.
- Run promoted models in paper mode for at least 60 trading sessions per market.
- Fail closed on missing, stale, malformed, drifting, or incompatible inputs.

## Non-Goals

- Do not build a never-losing or guaranteed-profit bot.
- Do not target a fixed win rate or classification accuracy.
- Do not use deep learning, reinforcement learning, gradient-boosted trees, or an ensemble in the first implementation.
- Do not trade options, futures, leveraged products, short positions, or instruments other than SPY and NIFTYBEES.
- Do not combine US and India rows into one model.
- Do not let an ML output determine position size, stops, targets, broker, account, or order type.
- Do not retrieve credentials from Chrome, browser storage, screenshots, chat, or source control.
- Do not activate Groww live trading or submit a real-money broker order.
- Do not shorten the 60-session paper observation period based on backtest performance.

## Scope And Market Isolation

The two lanes share implementation interfaces but not learned state.

| Property | SPY lane | NIFTYBEES lane |
| --- | --- | --- |
| Market | US | India |
| Data source | Alpaca Market Data API | Groww Historical Candle API |
| Bar interval | 1 day | 1 day |
| Execution during this build | Alpaca paper account | Local Market Sentinel paper simulator |
| Currency | USD | INR |
| Calendar | US exchange calendar | NSE calendar |
| Model artifact | SPY-specific | NIFTYBEES-specific |
| Cost configuration | US-specific | India-specific |
| Promotion result | Independent | Independent |

A passing SPY model cannot satisfy a NIFTYBEES gate, and a passing NIFTYBEES model cannot satisfy a SPY gate. Dashboard summaries may display both lanes, but they must not aggregate their evidence into one readiness result.

## Authority Boundary

The decision path is:

1. Market-data validation accepts a completed daily bar.
2. Feature generation builds a point-in-time feature row.
3. The deterministic strategy decides whether a candidate entry exists.
4. The active market-specific meta-labeler returns a probability and pass or abstain result.
5. A passed candidate becomes a protected `OrderIntent`.
6. `RiskAgent` evaluates the intent.
7. `ComplianceGuard` evaluates the intent and environment.
8. `ExecutionAgent` is the only component that may call a broker adapter.

The model has no reference to broker clients or `ExecutionAgent`. A missing or failed model blocks the candidate; it does not fall back to unfiltered live execution. Baseline strategy evaluation remains available only inside research and paper reports.

## Data Acquisition

### SPY Through Alpaca

Use Alpaca's historical stock bars endpoint at `https://data.alpaca.markets/v2/stocks/bars` with:

- symbol `SPY`;
- timeframe `1Day`;
- ascending sort;
- `adjustment=all`;
- explicit start and end dates; and
- pagination until `next_page_token` is absent.

Persist the requested feed, adjustment mode, retrieval timestamp, query range, response-page count, and source identifier with the dataset manifest. Credentials remain process-local and never enter the dataset or logs.

### NIFTYBEES Through Groww

Use Groww's current historical candle SDK or REST operation corresponding to `GET /v1/historical/candles`. Do not use the deprecated `/v1/historical/candle/range` operation.

Resolve and validate the NSE CASH Groww symbol before download rather than trusting an unchecked free-text ticker. Request one-day candles from the earliest supported date required by the run through the last completed NSE session. Groww documents cash-market history from 2020 onward; the manifest records the actual first and last returned trading dates.

If the Groww response does not declare corporate-action adjustment semantics, record the mode as `provider-unspecified`. Do not describe those bars as adjusted, combine them with an adjusted series, or train through an unexplained split or distribution discontinuity. The lane remains blocked until the discontinuity is reconciled against an authoritative instrument or corporate-action record.

Credentials remain process-local. Raw API responses and errors must be sanitized before logging.

### Immutable Raw Cache

Store normalized raw bars in a market-specific cache keyed by provider, instrument, interval, date range, adjustment mode, and response checksum. A refresh appends or replaces only the affected retrieval artifact; it never silently mutates a dataset already referenced by a model version.

## Canonical Bar Contract

Each normalized daily bar contains:

- provider and provider instrument identifier;
- canonical symbol and market;
- exchange trading date;
- source timezone;
- open, high, low, close, and volume;
- adjustment mode;
- source retrieval timestamp; and
- source response checksum.

Validation rejects a dataset with any of the following:

- duplicate or non-increasing trading dates;
- missing required values;
- non-positive prices;
- negative volume;
- high below open, close, or low;
- low above open, close, or high;
- bars later than the last completed market session;
- an unexpected symbol, market, interval, currency, or adjustment mode; or
- a date gap that is not explained by the configured exchange calendar.

Provider dates remain exchange trading dates. UTC conversion must not shift a daily bar into a neighboring trading date.

## Decision Timing And Leakage Control

A row for trading date `D` is created only after the `D` daily bar is complete. Features may use bars up to and including `D`. The earliest eligible order is the next market session, `D+1`.

Labels may inspect future bars only inside the training-dataset builder. Feature generation and runtime inference never receive those future bars. Training examples carry explicit `feature_as_of`, `entry_eligible_at`, and `label_end_at` fields so tests can prove the boundary.

No centered windows, backward-filled future values, randomly shuffled splits, or whole-dataset scaling are permitted. Scaling parameters are fitted inside each training fold only.

## Feature Set

The first model uses a fixed, reviewable feature set:

- 5-session close return;
- 20-session close return;
- 60-session close return;
- 20-session realized volatility of daily returns;
- current close distance from the 20-session moving average;
- current close distance from the 60-session moving average;
- current volume divided by 20-session average volume; and
- drawdown from the trailing 60-session closing high.

At least 61 completed bars are required before a feature row can be produced. Feature names, formulas, window lengths, and numerical handling form a versioned feature-schema identifier. Changing any of them invalidates existing models until retraining and validation complete.

## Deterministic Candidate Strategy

The long-only candidate strategy emits at most one market candidate per session when all of these are true:

- 20-session return is positive;
- close is above the 60-session moving average;
- volume is positive and the configured liquidity check passes;
- 20-session volatility is below the configured maximum.

Research creates a row for every market candidate, including overlapping label horizons. The purge gap prevents those overlapping horizons from leaking across folds. During chronological strategy replay and paper operation, the position-state gate suppresses a candidate whenever a position is already open for the instrument.

The strategy, not ML, defines market candidacy and position-state eligibility. Protection and quantity remain owned by existing strategy and risk configuration. The initial protected-trade defaults remain a 2 percent stop-loss and 3 percent take-profit, with a maximum holding period of 10 sessions. These values are embedded in the dataset and model manifests. Any change requires relabeling and retraining.

## Labels And Cost Model

For each deterministic candidate, simulate entry at the next session's open plus adverse spread and slippage. Evaluate the same protected stop, target, and 10-session maximum holding period used by the strategy.

Daily bars cannot reveal whether a stop or target traded first when both prices fall inside one bar. The labeler therefore applies these conservative deterministic rules:

- a gap through the stop exits at the opening price when that price is worse than the stop;
- a gap through the target exits at the target rather than granting favorable opening improvement;
- if both stop and target are touched during one daily bar, the stop is treated as first; and
- a position that reaches neither barrier exits at the tenth session's close with adverse exit slippage.

Calculate net outcome after market-specific:

- commissions and brokerage;
- regulatory fees and taxes;
- modeled bid-ask spread;
- modeled slippage; and
- other explicitly configured per-order costs.

Cost values are configuration inputs with source notes and effective dates. Historical labeling selects the cost schedule effective on the simulated trade date. Training fails when a required market cost profile is missing; it does not silently assume zero cost.

The meta-label is `1` only when the simulated protected trade has positive net P&L. Break-even and losing outcomes receive `0`. The row records gross P&L, each cost component, net P&L, exit reason, exit date, and holding sessions for audit and analysis.

## Model Pipeline

Train one regularized logistic-regression classifier per market. Each fold pipeline contains:

1. missing-value rejection;
2. feature standardization fitted on that fold's training rows;
3. logistic regression with fixed solver and reproducible seed; and
4. probability output for the positive meta-label.

Hyperparameters are a small predeclared set recorded in the trial ledger. The initial implementation may compare only regularization strengths from `{0.1, 1.0, 10.0}`. It must not perform an open-ended search.

The pass threshold is selected from `{0.55, 0.60, 0.65}` using training and calibration data only. Test-fold results cannot influence threshold selection. The model abstains below the frozen threshold.

A chronological calibration slice at the end of each pre-test window contains 20 percent of the available pre-test candidates, with a minimum of 40 rows and both label classes present. A 10-session gap separates the fit slice from calibration, and another 10-session gap separates calibration from test.

Fit the scaler and base logistic model on the fit slice only. Fit a sigmoid probability-calibration mapping and select the pass threshold on the calibration slice only. Apply both frozen stages to the test fold. If any slice cannot satisfy the row, class, or gap requirements, that fold and model are ineligible for promotion.

## Walk-Forward Validation

Validation uses expanding chronological folds:

- at least three test folds;
- a 10-session gap between training or calibration rows and each test fold;
- no overlap between a row's label horizon and a later fold boundary;
- scaling and model fitting repeated independently inside each fold; and
- test predictions collected exactly once per candidate.

Promotion requires at least 150 out-of-sample candidate rows in total, including at least 30 positive and 30 negative labels. Each test fold must contain at least 30 candidates. If a market cannot meet these minimums, its model remains research-only.

Classification metrics use the one-time test prediction for every candidate row. Trading metrics are calculated separately by replaying each test fold chronologically with the open-position gate, protected exits, costs, and the frozen ML threshold. This prevents overlapping research labels from being counted as simultaneously executable positions.

## Metrics And Promotion

Classification accuracy is reported but is not a promotion gate. Each market is promoted independently only when all of these hold out of sample:

- filtered net expectancy per completed replay trade is defined and positive in every fold;
- filtered net expectancy exceeds the unfiltered deterministic baseline in aggregate;
- filtered maximum drawdown is no worse than the unfiltered baseline in every fold;
- Brier score beats a constant-probability predictor based on the training prevalence;
- acceptance coverage is between 10 and 80 percent of deterministic candidates;
- minimum row and class counts are satisfied; and
- every dataset, feature, cost, parameter, and threshold trial is recorded.

The report also includes net return, gross return, total costs, completed outcomes, win rate, precision, recall, Brier score, calibration buckets, expectancy, maximum drawdown, acceptance coverage, and rejected-candidate count. No isolated metric may be presented as proof of future profitability.

A failed fold fails promotion. The system does not average away a failed mandatory gate.

## Trial Ledger And Selection Bias

Every attempted model configuration receives an immutable trial record containing:

- market and symbol;
- dataset checksum and date range;
- feature-schema version;
- label and cost-profile versions;
- fold definitions;
- hyperparameters and threshold candidates;
- all fold metrics;
- aggregate metrics;
- promotion result and failure reasons; and
- code version or commit identifier.

Repeated experiments remain visible. Reports include the number of attempted configurations so users can assess selection risk. Deleting failed trials is not part of the normal workflow.

## Model Artifacts

Each saved artifact contains or references:

- market and symbol;
- model type and library version;
- fitted feature order and scaling parameters;
- logistic coefficients and intercept;
- frozen pass threshold;
- training, calibration, and test date ranges;
- dataset, feature, label, and cost-profile identifiers;
- fold and aggregate metrics;
- promotion state;
- creation timestamp; and
- parent champion version when applicable.

The active pointer is market-specific. Loading rejects an artifact whose market, symbol, schema, library version, or checksum is incompatible with the runtime lane.

## Paper Operation

Historical promotion enables paper eligibility only.

- SPY candidates may flow through the normal risk and compliance path to an Alpaca paper account.
- NIFTYBEES candidates flow through the same internal decision path to the local paper simulator; Groww receives no order.

Each lane must accumulate at least 60 completed market sessions after activation. The paper report includes prediction coverage, realized protected outcomes, costs, drawdown, data failures, broker or simulator rejects, and model drift signals.

The 60-session clock is market-specific and cannot be backfilled with historical results. A model replacement restarts the clock for that lane unless the replacement changes only non-behavioral metadata.

## Retraining And Champion-Challenger Flow

Retraining is scheduled no more than monthly. It creates a challenger and never overwrites the active champion.

The challenger must pass the full historical validation suite. If it fails, the champion remains active and the failure is audited. If it passes, it becomes the paper champion for that market and begins a new 60-session observation period.

No model is automatically promoted to real-money eligibility. Paper completion creates evidence for a future human review; it does not alter broker readiness or runtime mode.

## Drift And Runtime Failure Behavior

The runtime blocks new entries and emits a sanitized audit event when:

- the expected daily bar is stale or missing;
- the feature schema differs from the active artifact;
- a feature is missing, non-finite, or outside validated safety bounds;
- model loading or inference fails;
- the market or symbol does not match the artifact;
- the active model is absent or not promoted for paper use;
- probability output is outside `[0, 1]`; or
- an upstream risk, compliance, account, market-hours, or broker gate fails.

Each artifact stores fit-slice means, standard deviations, and decile boundaries. A runtime feature more than eight fit-slice standard deviations from its mean is a hard outlier and blocks that candidate. After at least 60 scored candidates, a population stability index above `0.25` for any feature is material distribution drift and blocks new entries for that lane. Until 60 candidates exist, population drift is reported as insufficient history rather than passed.

Calibration drift is reported once enough resolved paper labels exist but is not used to reduce the threshold automatically. Drift never triggers automatic retraining, threshold reduction, or live activation. Material drift blocks new entries until a new challenger passes validation.

## Dashboard And CLI

The CLI gains explicit data-download, dataset-build, train, validate, promote-to-paper, and paper-status operations. Commands that perform historical research cannot instantiate live broker adapters.

The dashboard presents each lane separately with:

- mode and execution target;
- data source, range, freshness, and checksum;
- active model and feature-schema versions;
- frozen threshold and acceptance coverage;
- fold and aggregate metrics;
- total modeled and realized costs;
- maximum drawdown and net expectancy;
- paper-session count out of 60;
- latest drift and data-quality state; and
- blocked reasons.

It must not display credentials, promise profitability, provide a manual `ready_to_trade` control, or allow direct order submission.

## Security And Credential Handling

- API credentials are read only from the existing local secret-entry workflow or process environment.
- Credentials are never read from Chrome, browser storage, chat, screenshots, clipboard history, source files, dataset manifests, model artifacts, or audit logs.
- Previously exposed credentials must be revoked and regenerated before broker connectivity checks.
- Download and paper operations log only sanitized provider status and non-secret identifiers.
- RUFLO remains a supervised coordinator with no discretionary trading, model-promotion, or broker-order authority.

## Test-Driven Implementation

Implementation begins with failing tests for:

- Alpaca pagination and `adjustment=all` request mapping;
- Groww current historical-candle SDK mapping and deprecated-path rejection;
- market-specific credential redaction;
- canonical OHLCV validation and exchange-date preservation;
- feature warmup and exact formulas;
- no feature access after its decision timestamp;
- next-session entry eligibility;
- protected-trade labeling and every cost deduction;
- conservative same-bar, gap-through, and maximum-hold fill ordering;
- separate SPY and NIFTYBEES datasets, artifacts, thresholds, and active pointers;
- fold-local scaling and chronological calibration;
- 10-session purge-gap enforcement;
- threshold selection without test-fold access;
- all promotion gates and failure reasons;
- immutable trial-ledger records;
- incompatible artifact rejection;
- stale data, drift, and inference failures blocking candidates;
- hard-outlier and population-stability drift thresholds;
- ML code having no broker or execution authority;
- SPY using only Alpaca paper execution;
- NIFTYBEES using only the local simulator; and
- independent 60-session paper clocks.

After focused tests pass, run the full Python suite and dashboard build. Broker calls use mocks during automated tests. Verification submits no real-money order.

## Rollout

1. Add market-data clients and immutable normalized caches.
2. Add point-in-time dataset, feature, label, and cost-profile builders.
3. Add market-specific logistic pipelines, walk-forward validation, and trial ledger.
4. Replace synthetic model promotion and migrate model-store metadata.
5. Add separate paper runners and dashboard status.
6. Run historical validation for each lane independently.
7. Activate only passing models for paper observation.
8. Accumulate and report 60 market sessions per lane.
9. Leave live trading blocked pending a separate future review and all broker gates.

If either provider contract or dataset cannot support the design, that lane remains blocked while the other lane may continue independently.

## Acceptance Criteria

The implementation is complete when:

- synthetic training data no longer drives an active model;
- both market lanes can download, normalize, and audit real daily data independently;
- deterministic candidates and meta-labels are point-in-time and cost-aware;
- each model is validated with the required walk-forward gaps and gates;
- failed models cannot become paper-active;
- SPY paper execution cannot reach an Alpaca live endpoint;
- NIFTYBEES paper execution cannot reach Groww order APIs;
- ML has no path to broker execution or runtime activation;
- dashboard and CLI show separate, sanitized evidence for each market;
- the full test suite and dashboard build pass; and
- no real-money order is placed during implementation or verification.
